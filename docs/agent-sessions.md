# Агентные сессии для DevOps проекта

Статус: dual-stack MVP принят; назначены FINAL-01 и FINAL-05; актуальные назначения и результаты — в [реестре](status.md). Архитектура, приоритеты и критерии полной готовности — в [плане реализации](implementation-plan.md). Карточки MVP сохраняют исходные задания, завершенные по [контракту v3](contracts.md); FINAL-01 и FINAL-05 выполняются по назначению пользователя, остальные карточки FINAL остаются планом. Эти карточки предназначены для отдельных последовательных или параллельных сессий; в них включены функции из пользовательского `hackathon_features.md`.

Каждая сессия заканчивается конкретным результатом и отчетом `docs/reports/<ID>.md`. Назначение этапа целиком означает работу до его приемки; назначение одной карточки ограничивает работу этой карточкой. FINAL начинается после приемки MVP и отдельного назначения пользователем.

## Организация работы

Интегратор сначала фиксирует контракт, затем выдает каждому агенту базовую ревизию, worktree, каталог и ID задачи. Он один редактирует общие `config/versions.yaml`, `config/images.lock.yaml`, `docs/contracts.md`, Makefile, основной deploy, README и статусный реестр. Остальные предлагают изменения этих файлов через свой отчет; интегратор применяет их до зависимой работы, если меняется контракт.

| Область | Владелец | Пути для разработки |
| --- | --- | --- |
| Общая сборка и контракты | Интегратор | `Makefile`, `config/versions.yaml`, `config/images.lock.yaml`, `docs/contracts.md`, `scripts/deploy.*`, `docs/status.md`, `README.md` |
| Ubuntu и кластер | MVP-01 | `ansible/`, `deploy/storage/`, шаблон `config/environments/ubuntu.example.yaml` |
| Приложение и Gateway | MVP-02, затем FINAL-01 | `deploy/app/`, `deploy/gateway/`, `scripts/check-gateway.*` |
| Метрики и dashboards | MVP-03, затем FINAL-02 | `deploy/monitoring/`, `dashboards/`, `alerts/`, `scripts/check-metrics.*` |
| Логи | MVP-04 | `deploy/logging/`, `scripts/check-logs.*` |
| Сквозная приемка | MVP-05, MVP-06, FINAL-05/07 | `scripts/verify.*`, `tests/e2e/`, `scripts/evidence.*`, `docs/acceptance/`, `docs/passport/` |
| Политики доступа | FINAL-03 | `deploy/security/`, `tests/security/`, `scripts/check-security.*` |
| Выпуск canary и автооткат | FINAL-05 | `scripts/canary.*`, `tests/canary/`; изменение Gateway/values — через владельца FINAL-01 и интегратора |
| CI | FINAL-04 | `.github/workflows/` **или** `.gitlab-ci.yml`, `ci/`, `scripts/ci.*` |
| Дополнительные опции | FINAL-06 | Только выбранные в карточке отдельные пути |

Это целевые пути, а не требование создать пустой каркас всех функций сразу. MVP-00 определяет способ рендера собственных ресурсов; предпочтительно небольшие Helm charts и обычные values для сторонних charts. Один ресурс не управляется одновременно Helm и `kubectl apply`.

Статусы в `docs/status.md`: `todo`, `in_progress`, `ready_for_integration`, `done`, `blocked`. `ready_for_integration` означает готовый код с выполненными локальными проверками; `done` требует всех проверок карточки, включая live, если они обязательны. Реестр изменяет интегратор. Эти статусы не являются командами управления агентами.

Общий промпт для любой карточки:

> Выполни <ID> из docs/agent-sessions.md в пределах этапа из docs/implementation-plan.md. Прочитай AGENTS.md и docs/contracts.md. Проверь git status и базовую ревизию. Работай в назначенном worktree и своих каталогах; общие файлы и общую Ubuntu VM изменяет интегратор. Доведи задачу до ее проверяемого результата, обнови docs/reports/<ID>.md. Отдельно укажи pass, fail и not run с причинами. Не переходи к другим карточкам и не расширяй архитектуру. Для недостающего общего контракта предложи конкретную поправку интегратору и продолжай независимую часть.

## Этап MVP

### MVP 00 Контракт и стартовая ревизия

**Исполнитель:** интегратор. **Зависимости:** нет. **Ориентир:** одна короткая сессия до запуска параллельных задач.

Результат: остальные агенты могут работать независимо, не выбирая несовместимые версии, порты и способы установки.

1. Подготовить `AGENTS.md` с правилами двух этапов и владельцами файлов, `docs/contracts.md`, `docs/status.md`. В контракт перенести согласованные решения из плана, не переписывать заново его архитектуру.
2. Зафиксировать точные версии и image digests, включая transitive images chart, либо явный проверяемый lock для них. Сверить поддерживаемую комбинацию Kubernetes, Gateway API CRDs и Traefik. Убедиться, что Fluentd image действительно содержит Loki output plugin и необходимые parsers.
3. Согласовать namespaces, names/labels, ServiceMonitor selectors, HTTP ответ, log fields, host paths/PV, внешний NodePort, имена Helm release и интерфейсы check-скриптов. Задать `X-Request-ID` в запросе/ответе/access-log, передачу общего run ID между проверками и JSON формат отчета. Профили `mvp`/`final` имеют явный список обязательных checks; отсутствие нужной возможности окружения не превращается в пропущенную успешную проверку.
4. Определить доступ к выделенной Ubuntu VM, ее характеристики, сети/CIDR, способ получения второй чистой VM или snapshot. Реальные адреса передаются локальным inventory, пример содержит фиктивные значения.
5. Выбрать хостинг будущего публичного репозитория; при отсутствии предпочтения подготовить CI для GitHub, но не публиковать репозиторий в рамках этой карточки. Записать способ доступной локальной проверки вне хостинга.
6. Создать базовую ревизию на `main` и worktree для компонентных задач. В `.gitignore` исключить kubeconfig, локальный inventory, state, приватные ключи, credentials и сырые чувствительные логи.

**Приемка:** нет плавающих версий в принятой матрице; у всех компонентов понятен публичный источник или рецепт сборки; конфликтующих владельцев нет; каждый агент получил свой каталог и общие параметры. Матрица еще не считается runtime-проверенной: это подтверждается последующей интеграцией.

**Промпт:** «Выполни MVP-00. Подготовь контракт и исходную ревизию для параллельных MVP-01–04. Сейчас не реализуй final».

### MVP 01 Ubuntu и kubeadm

**Исполнитель:** агент инфраструктуры. **Зависимость:** MVP-00. **Пути:** `ansible/`, `deploy/storage/`, пример environment.

Результат: повторяемый переход от чистой Ubuntu 24.04 к готовому одноузловому Kubernetes.

- Проверить ОС/архитектуру, RAM/диск, hostname и адрес, время, доступ к репозиториям; подготовить swap, kernel modules/sysctl, containerd с рабочим CRI и согласованными systemd cgroups.
- Установить закрепленные kubeadm/kubelet/kubectl, выполнить init только при отсутствии кластера; при повторном запуске проверить идентичность и состояние существующего кластера. Не заменять ошибку автоматическим reset.
- Установить Calico и дождаться сети; разрешить workload scheduling на единственном control-plane. Gateway/logging/monitoring pods и DaemonSets должны планироваться с учетом taints.
- Подготовить kubeconfig с ограниченными файловыми правами, health-проверки node/DNS/pod network и данные для интегратора. Не включать kubeconfig в artifacts.
- Создать каталоги хранения, UID/GID, StorageClass для local PV, сами PV с node affinity и Retain. Договориться о claim bindings с MVP-03/04; PV не остаются Pending из-за отсутствующего provisioner.
- Описать требования к сетевому доступу к VM и порты. Не менять homelab router и действующие сервисы по ходу задачи.

**Приемка:** чистая VM дает Node Ready и работающий DNS/pod network; повтор bootstrap проходит без разрушения; PV доступны для ожидаемых PVC. После контролируемого reboot kubelet/containerd и сеть восстанавливаются. Не готовые внешние предпосылки явно записаны.

**Промпт:** «Выполни MVP-01 по закрепленной матрице. Подготовь bootstrap Ubuntu и kubeadm, сеть и local PV. Передай интегратору проверку чистого и повторного запуска».

### MVP 02 Приложение и Gateway API

**Исполнитель:** агент Gateway. **Зависимость:** MVP-00; live-проверка требует MVP-01. **Пути:** `deploy/app/`, `deploy/gateway/`, `scripts/check-gateway.*`.

Результат: запрос снаружи кластера проходит через Gateway API и получает проверяемый ответ Nginx.

- Развернуть публичный закрепленный Nginx: ConfigMap со страницей `Hello World!`, Deployment и ClusterIP Service. Приложение не получает собственного NodePort/Ingress для обхода Gateway.
- Настроить readiness/liveness, requests/limits, non-root, read-only root filesystem с отдельными writable tmp/cache томами, drop capabilities и отсутствие ненужного ServiceAccount token.
- Вывести JSON access-log в stdout, error-log в stderr. Добавить воспроизводимый missing-file сценарий для настоящей error-записи; обычный `return 404` может не создавать нужный error-log.
- Обеспечить передачу `X-Request-ID` через Gateway, запись в JSON access-log и возврат того же ID в HTTP-ответе. Для отсутствующего/некорректного входного ID определить безопасный fallback средствами Nginx; ограничить формат и длину. Уникальный URI missing-file запроса остается способом найти error-log, который не обязан содержать HTTP header.
- Установить Traefik с включенным Gateway provider, RBAC, Gateway API CRDs из зафиксированного Standard channel и единственными GatewayClass/Gateway/HTTPRoute. CRDs устанавливаются до зависимых ресурсов, их готовность ожидается явно.
- Настроить внешний NodePort Traefik и закрытый metrics Service, заранее согласованный с MVP-03. При NodePort проверить способ заполнения Gateway status выбранной версией controller, не ждать несуществующего облачного IP.
- Проверить актуальные `Accepted`, `Programmed`, `ResolvedRefs` на соответствующих ресурсах и `observedGeneration`, затем выполнить внешний HTTP запрос. Port-forward непосредственно к приложению не является приемкой Gateway.

**Приемка:** HTTP 200, точное тело и ожидаемый `X-Request-ID` через IP VM и NodePort; Gateway conditions успешны; неправильный маршрут не выдает успешный ответ приложения; stdout/stderr формируются; доступен metrics endpoint Traefik.

**Промпт:** «Выполни MVP-02: Nginx, Traefik и настоящий Gateway API. Подготовь внешний HTTP smoke, access/error логи и контракт метрик для MVP-03».

### MVP 03 Prometheus и реальные метрики

**Исполнитель:** агент мониторинга. **Зависимость:** MVP-00; live-проверка после MVP-01/02. **Пути:** `deploy/monitoring/`, `scripts/check-metrics.*`.

Результат: Prometheus действительно получает данные развернутого решения и позволяет проверить HTTP-трафик.

- Настроить закрепленный kube-prometheus-stack: Prometheus/Operator, node exporter, kube state metrics; Grafana/Alertmanager пока выключены. Установить PV/PVC привязки, лимиты retention/time/size и requests/limits.
- Подключить ServiceMonitor Traefik. Установить порядок CRDs → operator → мониторируемые объекты и проверить namespace/release selectors, RBAC и ports.
- Убрать или обоснованно настроить targets, недоступные в выбранном kubeadm профиле. Не скрывать реально заявленные неработающие targets.
- Реализовать проверку `/api/v1/targets` и `/api/v1/query`: `up` нужного target, свежая реальная метрика, изменение HTTP counter после нагрузки. Скрейп собственного Prometheus не считается достаточной демонстрацией инфраструктуры.
- Предоставить интегратору операции снимка counter до/после общей HTTP-пробы. Проверка учитывает scrape interval, рестарты/reset и фоновый трафик; для точного сравнения выделяет фиксированный тестовый route или scope, не создавая metric label на каждый Request-ID. В evidence записываются query, временное окно, исходное/итоговое значения и число тестовых запросов.
- Зафиксировать реальные metric names/labels и рабочие queries. Нулевой трафик допустим, отсутствие target/sample — отдельная ошибка; request IDs не используются как metric labels.

**Приемка:** нужные targets живы, queries возвращают значения, HTTP counter увеличивается; тест ограничен по времени и не принимает пустой vector за успех. Старые samples сохраняются после рестарта Prometheus pod на его PVC.

**Промпт:** «Выполни MVP-03. Настрой Prometheus и проверку метрик Traefik и инфраструктуры через query API, включая изменение счетчика после HTTP-запросов».

### MVP 04 Fluentd и поиск логов в Loki

**Исполнитель:** агент логирования. **Зависимость:** MVP-00; live-проверка после MVP-01/02. **Пути:** `deploy/logging/`, `scripts/check-logs.*`.

Результат: оба потока логов Nginx проходят через обязательный Fluentd и находятся в отдельной системе хранения.

- Развернуть Loki в однопроцессном режиме с локальным persistent filesystem, совместимой схемой, ограничением retention и потребления ресурсов. Использовать один экземпляр без внешнего object storage и кэшей, не нужных этому стенду.
- Настроить Fluentd DaemonSet, read-only доступ к нужным CRI файлам, корректные пути и symlinks `/var/log/containers`/`/var/log/pods`, парсинг timestamp/stream/message, затем JSON access-log. Error-log не должен исчезать из-за не-JSON формата.
- Обеспечить права чтения, позиции чтения и bounded file buffer вне ephemeral container filesystem. Если нужны Kubernetes metadata, дать только необходимые read-права; cluster-admin не использовать.
- Labels ограничить приложением, namespace, container, stream и фиксированными признаками. Request ID хранить в записи, исключить сбор собственных collector логов в бесконечный цикл.
- Скрипт умеет проверять Request-ID из общего verify-прогона и опрашивает Loki API до появления access-записи именно Nginx с нужным ID, методом, путем и статусом. Для самостоятельного запуска создает собственную HTTP-пробу. Отдельно проверяет настоящий missing-file error по уникальному URI; общий verify не подменяет один запрос другим внутри компонентных проверок.
- Проверить restart Fluentd, повторную доставку после короткого разрыва связи и понятное поведение при заполнении буфера. Подробный fault drill будет в FINAL-05.

**Приемка:** оба потока находятся в Loki, с корректным временем и источником; `kubectl logs nginx` не подменяет проверку Loki. Рестарт collector не обнуляет сохраненные позиции; непроверенные гарантии потерь/дубликатов не заявляются.

**Промпт:** «Выполни MVP-04: Fluentd → Loki, контейнерные access/error логи, persistent positions/buffer и smoke по уникальному HTTP-маркеру».

### MVP 05 Общая автоматизация и идемпотентность

**Исполнитель:** интегратор. **Зависимости:** готовый код MVP-01–04. Разработку общей обвязки можно вести раньше.

Результат: один понятный путь установки и одна команда проверки всех обязательных частей — основа Self-Verifying Kubernetes Stack.

- Объединить компонентные ветки, реализовать команды из контракта. Установка: preflight/bootstrap → CNI/storage → нужные CRDs/controllers → компоненты → application route → ожидание готовности → verify. Конкретный порядок ServiceMonitor определяется готовностью monitoring CRDs.
- Согласовать все values с единым environment и version lock. Hostname, IP, namespace и порты не копировать вручную между конфигурациями.
- Объединить HTTP/metrics/logs checks, автоматический loopback port-forward и cleanup временных процессов. Read-only проверки не должны требовать ручного редактирования ресурсов.
- Реализовать единый сценарий: readiness и Gateway conditions → снимок HTTP counter → запрос с `X-Request-ID` → проверка статуса/тела/ответного ID → ожидание свежего scrape и увеличения counter → поиск этой access-записи в Loki. Отдельная error-проба проходит тот же Gateway. Изменение агрегированного counter не объявляется трассировкой Request-ID.
- Добавить базовые runtime-проверки приложения: ненулевой UID, read-only корневой mount, отсутствие effective capabilities и ненужного ServiceAccount token. Не считать `Permission denied` достаточным доказательством read-only filesystem. Сетевые инварианты подключает FINAL-03, до этого они не объявляются реализованными.
- Запустить deploy дважды и проверить stable resource identity, отсутствие дубликатов, сохранение PVC и секретов, прохождение повторного verify. Повторный bootstrap проверить отдельно.
- Реализовать читаемый итог и `artifacts/verify/<run-id>/report.json`: профиль, ревизия, ОС/версии, время, все checks со статусами/ожиданиями/фактическими результатами, Gateway conditions, Request-ID, HTTP ответ, metric queries/значения и Loki match. При ошибке приложить ограниченные по объему events/logs; не выгружать все Secrets или kubeconfig. Отчет создается и при timeout/отказе; `make evidence` собирает уже полученные результаты.
- Описать ожидаемые ошибки: недоступен registry, недостаточно ресурсов, зависший PVC, несовместимые CRDs, отсутствует target/лог. Для каждой — диагностическая команда и следующий шаг.

**Приемка:** `bootstrap`, `deploy`, `verify` и `verify-idempotency` успешны на выделенном kubeadm стенде; каждый обязательный компонент проверен после интеграции. Отсутствующий target, неверный HTTP ответ/ID или не найденный лог дает ненулевой exit code и указывает конкретный check в JSON. Общий run ID позволяет сопоставить все доказательства одного прогона.

**Промпт:** «Выполни MVP-05: интегрируй компоненты, доведи общий deploy и сквозной verify с Request-ID и JSON отчетом до успеха, проверь повторные запуски и собери evidence без секретов».

### MVP 06 Чистая приемка и документация

**Исполнитель:** агент приемки; правки общих файлов вносит интегратор. **Зависимость:** MVP-05.

Результат: MVP можно развернуть по репозиторию человеку, который не знает homelab.

- Использовать чистую Ubuntu 24.04 VM и свежий checkout. Установка на уже подготовленном первом стенде не заменяет этот сценарий.
- Выполнить только инструкцию README; зафиксировать все скрытые предпосылки. Исправления возвращать в автоматизацию и повторять затронутые проверки, не «донастраивать руками».
- Проверить отсутствие обязательных обращений к домашним доменам, registry, DNS, Prometheus/Loki, NFS и соседним репозиториям. Проверка публичного анонимного clone окончательно выполняется при публикации в FINAL-07.
- Измерить время установки, RAM/CPU/диск; записать проверенную ОС, ресурсы и версии. Просмотреть failure messages и проверить, что команды из README совпадают с реальными.
- Подготовить README, архитектуру и черновик паспорта по структуре задания; сформулировать single-node/local-PV ограничения. Составить таблицу «требование → файл → команда → доказательство».
- Зафиксировать принятую MVP ревизию и выдать итог `MVP accepted` только после всех пунктов gate из основного плана.

**Приемка:** установка, HTTP, метрики, access/error логи и повторный deploy прошли на чистой VM; документация достаточна для повторения. Все дальнейшие изменения final начинаются от этой рабочей базы.

**Промпт:** «Проведи MVP-06 как независимый проверяющий: чистая Ubuntu, свежий checkout, только README. Найди и устрани с интегратором скрытые зависимости, оформи приемку MVP».

## Этап final

### FINAL 01 Расширенный Gateway API

**Зависимость:** принят MVP. **Владелец:** агент Gateway. **Пути:** те же, что в MVP-02.

Добавить второй backend Nginx. На основном маршруте оба здоровых backend сохраняют тело `Hello World!`, а версия различается по заголовку `X-Release: stable` или `canary`; это позволяет обычному verify работать и при 90/10. Настроить независимые HTTPRoute с hostname и path, затем weighted backendRefs для stable/canary. Все дополнительные поведения должны быть выражены Gateway API; Traefik-specific расширения добавлять только при необходимости и явно описывать.

Подготовить контракт для FINAL-05: отдельно закрепленные stable/canary версии и ответы, параметризованные веса, начальное состояние 100/0 и тестовые маршруты к каждому backend через Gateway. Они нужны для детерминированного smoke кандидата даже при нулевом весе общего маршрута. Контракт фиксирует также labels/queries для метрик canary и проверку окончания применения новой конфигурации. Сам сценарий принятия решения и автоотката принадлежит FINAL-05; второй писатель HTTPRoute не появляется.

Добавить HTTPS listener и TLS Secret. Базовый воспроизводимый вариант — локально сгенерированные CA и сертификат для `.test`, проверка `curl --cacert --resolve`, без купленного домена и без обязательного `-k`. Ключи не коммитятся и не перегенерируются каждым deploy. Публичный ACME остается необязательной опцией. При HTTP redirect указать реально доступный HTTPS порт NodePort и проверить Location.

**Приемка:** hostname/path доходят до ожидаемых backend; TLS проверяет цепочку и имя. Для traffic splitting выполнить достаточную выборку, например 1000 запросов без retries, проверить обе метки `X-Release` и разумный статистический интервал доли canary, а не точное равенство 90/10. Затем вернуть 100/0 и подтвердить, что новый трафик общего маршрута идет только в stable. Отдельные тестовые маршруты достоверно различают backend; они не входят в измерение доли пользовательского трафика. Базовый MVP smoke остается зеленым.

**Промпт:** «Выполни FINAL-01: host/path, два backend, TLS и traffic splitting. Подготовь FINAL-05 контракт раздельного smoke backend, метрик и управления весами через общий release».

### FINAL 02 Dashboards и эксплуатационные alerts

**Зависимость:** принят MVP; selectors FINAL-01 согласуются через контракт. **Владелец:** агент мониторинга.

Включить Grafana и Alertmanager, provision datasource и не более трех содержательных dashboards: HTTP/Gateway, ресурсы Kubernetes, логи/состояние наблюдаемости. Добавить поиск access-log по Request-ID и представление stable/canary: фактическое число запросов, error rate и latency каждого backend. ### FINAL 03 Проверяемая безопасность

**Зависимость:** принят MVP и закреплены требуемые потоки; live после согласования FINAL-01/02. **Владелец:** агент политик.

Ограничить ingress/egress namespace приложения через NetworkPolicy, явно разрешить Traefik → app, нужный DNS и необходимые потоки наблюдаемости. Логи читаются collector с узла и идут в Loki; не добавлять выдуманный сетевой app → Fluentd канал. Сначала защитить application boundary, затем расширять изоляцию только при наличии положительных и отрицательных тестов.

Включить в `scripts/check-security.*` явную матрицу проверок:

| Инвариант | Доказательство |
| --- | --- |
| Gateway → app разрешено | Реальный HTTP запрос через Gateway с ожидаемым ответом |
| Prometheus → metrics разрешено | Успешный scrape и свежая sample именно нужного target |
| Посторонний pod → app запрещено | Из тестового pod без разрешенных labels соединение блокируется; разрешенная контрольная проба к тому же backend проходит |
| App → Kubernetes API запрещено | Из сетевого контекста app блокируется соединение к API Service и применимому endpoint; контрольная проба из разрешенного контекста доказывает, что сам API доступен |
| securityContext реально применяется | Проверены UID процесса, effective capabilities, read-only root mount и отсутствие ненужного API token; writable tmp/cache остаются работоспособны |

HTTP 401/403 от API означает успешное сетевое соединение и не подтверждает запрет egress. На одноузловом kubeadm отдельно проверить Service DNAT и доступ к API на узле с учетом поведения Calico; при необходимости добавить scoped Calico policy только для app и явно зафиксировать эту зависимость. Недоступность диагностической утилиты или самого endpoint не считается доказательством запрета. Недостаточную сетевую изоляцию нельзя заменить одним `automountServiceAccountToken: false`.

Проверить права collector, hostPath, ServiceAccounts, отсутствие admin token в прикладных pod, доступность административных Service и секреты. Применимые к приложению non-root/read-only/capability настройки уже входят в MVP. Исключения node exporter, CNI и Fluentd документировать отдельно; не распространять на них слепо policy restricted, которая делает стек неработоспособным.

Изменения чужих Deployment/values передавать владельцам через интегратора. CRDs/RBAC/CNI не изменять параллельно с другим оператором общей VM.

**Приемка:** все строки матрицы реально проверены и входят в `make verify ... PROFILE=final` с общим JSON отчетом. Интегратор подключает check-скрипт к общей команде. Проверки создают только свои временные pod, ограничены timeout и убирают их после завершения. На Calico разрешенный трафик проходит, запрещенный блокируется; Gateway, Prometheus и Loki smoke остаются зелеными. Отсутствие исполняющего CNI делает final verify неуспешным.

**Промпт:** «Выполни FINAL-03: security-инварианты в общем verify, включая Gateway/app, Prometheus/metrics, запрет постороннего pod и app → API, runtime securityContext. Подтверди их на Calico положительными и отрицательными тестами».

### FINAL 04 CI с одноразовым кластером

**Зависимость:** принят MVP для разработки; финальная приемка после интеграции FINAL-03/05. **Владелец:** агент CI. **Пути:** только выбранный CI provider, `ci/`, `scripts/ci.*`.

Pipeline использует те же скрипты, что разработчик и эксперт: shell/YAML/Ansible lint → Helm lint/render и проверка схем, включая custom resources → закрепленный kind с Calico → deploy → `make verify ... PROFILE=final` → сценарии canary/автоотката → повтор deploy и verify → artifacts/cleanup. Проверки MVP могут запускаться раньше отдельным профилем, но не подменяют приемку final. Чистая установка Ubuntu/kubeadm остается отдельным приемочным сценарием с отчетом.

Kind получает уникальные имя/context/порты/рабочие каталоги. Kubeconfig передается явно; случайное использование `current-context` домашнего кластера исключается. Сбор диагностики выполняется и при ошибке, cleanup удаляет только созданный этой job кластер. Images либо публичны и закреплены, либо собираются из репозитория и загружаются в kind автоматически.

Для полного final CI установить Calico совместимым способом и отключить конфликтующий default CNI. Если FINAL-03 потребовалась дополнительная Calico policy, применить и проверить ее также в kind. Общие runner resources сериализовать; отсутствие прав на Docker daemon/privileged kind является внешней предпосылкой, а не поводом пропустить integration tests.

Сохранять JSON отчеты verify и canary, включая неуспешные прогоны. Негативный canary-тест ожидает ненулевой код команды выпуска и доказанный возврат трафика 100/0; сам тест зеленый только при выполнении обоих условий и последующем успешном verify. Общий `|| true`, скрывающий реальные ошибки, не подходит.

**Приемка:** локальная команда CI проходит и имеет те же шаги в выбранном хостинге; hosted pipeline тоже реально запущен перед заявлением его успеха. Неверный route/selector, отсутствие логов, нарушение security-инварианта или несостоявшийся ожидаемый rollback делает pipeline красным, evidence сохраняется. Проверяющему не нужен домашний GitLab runner для разворачивания решения.

**Промпт:** «Выполни FINAL-04: переносимый CI со статикой, реальным disposable kind, сквозным smoke, повторным deploy и диагностикой отказов».

### FINAL 05 Автоматический откат canary и восстановление

**Зависимости:** принятые основные изменения FINAL-01–03; скрипты можно готовить заранее. **Исполнитель:** агент эксплуатации, live через интегратора.

Основной новый результат из `hackathon_features.md` — `make deploy-canary`: после выпуска кандидата система сама принимает решение по HTTP smoke и метрикам. Механизм реализуется скриптом поверх уже выбранных Helm/Gateway API, без обязательного Argo Rollouts или Flagger. Это конечный сценарий выпуска с ограниченным окном наблюдения; непрерывный контроль после его завершения не заявляется.

1. Захватить общую блокировку deploy, проверить готовность stable и наблюдаемости, сохранить принятую ревизию и эффективные values. Перед заменой кандидата привести общий маршрут к подтвержденному 100/0. Зафиксировать окно наблюдения, минимальное число запросов, порог ошибок, scrape interval и общий deadline в конфигурации; стартовые ориентиры для демо — 60–120 секунд, не менее 100 canary запросов и error rate не выше 1%, после измерения уточнить.
2. Развернуть закрепленного кандидата отдельно от stable при весах 100/0. Проверить его readiness и точный ответ через отдельный Gateway маршрут. Результат всегда должен отличать фактический canary от stable; случайная выборка общего 90/10 маршрута не заменяет этот smoke.
3. Включить 90/10 через штатный механизм управления release и дождаться применения HTTPRoute. Сгенерировать ограниченный трафик; собрать HTTP-результаты и свежие метрики canary. Успех требует одновременно правильных ответов, достаточной выборки и допустимого error rate. Можно оставить здоровый canary на 10%; автоматическое продвижение до 100% не входит в эту карточку.
4. При неверном ответе, 5xx выше порога, потере readiness или timeout вернуть 100/0. Если Prometheus недоступен, samples устарели либо запросов недостаточно, записать `inconclusive`, также вернуть 100/0 и завершить выпуск ненулевым кодом. Нет данных не означает ноль ошибок.
5. Проверить новые Gateway conditions и серию запросов общего маршрута: трафик идет в stable. Этот шаг подтверждает откат трафика; проверка восстановления конфигурации/версии release выполняется отдельно. При необходимости вернуть неудачный кандидат к прежней конфигурации или убрать его из активных workloads, чтобы штатный verify проходил. Повтор обычного deploy не должен возвращать rejected candidate в трафик.
6. При ошибке самого отката выдать отдельный `rollback_failed`, сохранить фактические веса/conditions и команду восстановления, завершиться ненулевым кодом. После прерывания процесса следующий запуск сначала проверяет и восстанавливает известное состояние 100/0; локальное состояние операции не подменяет чтение фактического кластера.
7. Записать `artifacts/canary/<run-id>/report.json`: ревизии stable/canary, пороги и временное окно, размер выборки, ответы/queries, причина решения, веса до/после и результат проверки rollback. Не создавать конкурирующий imperative patch поверх конфигурации, которой владеет Helm.

`make verify-canary` запускается на выделенном тестовом стенде и доказывает четыре сценария: здоровый кандидат принят; намеренно возвращающий 500 кандидат автоматически отвергнут; кандидат с HTTP 200 и неверным телом отвергнут; потеря метрик/недостаточная выборка дают `inconclusive` и возврат 100/0. Для проверки решения после включения 90/10 сбой вводится после начального успешного smoke, например переключением версионируемой demo-конфигурации Nginx. Неверное тело проверяется также до подачи общего трафика. Fault fixtures и cleanup принадлежат тесту; они не становятся поведением обычного приложения.

Добавить воспроизводимый `make demo` и отдельные сценарии, каждый с cleanup и проверкой штатного состояния:

- Удаление одного app pod и восстановление трафика; для демонстрации непрерывности включить две app replicas и подходящий rolling update. На одной VM это защита от отказа pod, не от отказа узла.
- Изменение ответа/конфигурации через версионируемый release, успешный rollout и rollback к известной ревизии. Конфигурация и checksum должны обеспечивать фактическое обновление pod, а не только ConfigMap.
- Короткая недоступность Loki: продолжить ограниченную генерацию запросов, восстановить Loki, найти весь заранее записанный набор маркеров после flush буфера. Проверить отсутствие бесконечного повторного чтения, допуская задокументированные дубли.
- Пересоздание Prometheus/Loki pod с сохранением старых данных в PVC; контролируемый reboot выделенной VM и повторный сквозной verify.
- Проверка отсутствия данных/сигнала и последующего alert resolved совместно с FINAL-02; негативные сценарии не оставляют стенд сломанным.

**Приемка:** сценарии canary реально выполняют автоматический возврат 100/0 без ручной правки маршрута; после отказа команда выпуска возвращает ненулевой код даже при успешном rollback. После cleanup общий final verify зеленый, повтор deploy не возвращает отвергнутый canary. Протокол каждого сценария содержит нагрузку, времена обнаружения/восстановления и фактический результат. Длительность отключения Loki ограничена емкостью буфера и retention; не обещается отсутствие потерь при произвольном outage. Рестарт с PVC не называется восстановлением из backup; последнее — отдельная опция FINAL-06.

**Промпт:** «Выполни FINAL-05: выпуск canary с HTTP/metrics gate и автоматическим возвратом 100/0, тесты здорового/сломанного кандидата и отсутствия данных. Добавь fault/recovery сценарии, отчеты решений и финальный зеленый verify».
