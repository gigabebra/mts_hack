## Функции из пользовательского наброска

Основная идея — **Self-Verifying Kubernetes Stack**: инфраструктура автоматически разворачивается и проверяет собственную работоспособность. Все шесть предложений из `hackathon_features.md` включены в существующие сессии; дополнительные параллельные владельцы не требуются.

| Функция | Что добавляем или уточняем | Этап и сессии |
| --- | --- | --- |
| Self-verification | `make verify` проверяет готовность, Gateway, HTTP, метрики, логи и применимые security-инварианты; выдает читаемый итог и JSON отчет, завершается ненулевым кодом при провале | Основа в MVP-05; полный набор final дополняет FINAL-03 |
| Canary deployment | Два backend stable/canary, измеряемое распределение 90/10, раздельная проверка здоровья backend | Маршруты в FINAL-01, управляемый выпуск в FINAL-05 |
| Автоматический rollback | Проверка кандидата после развертывания; при неверном ответе, превышении error rate или невозможности надежно проверить результат — возврат трафика на stable 100%, canary 0% | Новая основная функция FINAL-05, без обязательного дополнительного rollout controller |
| Проверяемые security invariants | Gateway → app и Prometheus → metrics разрешены; посторонний pod → app и app → Kubernetes API запрещены; права процесса и filesystem проверяются в runtime | Базовый securityContext в MVP-02/05; сетевые и полные runtime-проверки в FINAL-03 |
| Сквозная observability | Общий Request-ID связывает HTTP-ответ и access-log; в том же прогоне подтверждается увеличение scoped HTTP counter в Prometheus | Общий контракт MVP-00, реализация MVP-02–05, представление в FINAL-02 |
| CI с ephemeral Kubernetes | Один pipeline создает кластер, выполняет deploy и тот же `make verify`; final использует Calico и дополнительно проверяет отказ canary и автооткат | FINAL-04 совместно с FINAL-03/05 |

Request-ID хранится в логах и отчете, а метрики остаются агрегированными по ограниченному набору labels. Проверка фиксирует счетчик до и после тестового трафика и временное окно; Prometheus не используется как трассировка отдельного Request-ID.

## Предлагаемая архитектура

```text
Эксперт или пользователь
  │ HTTP на IP виртуальной машины и NodePort
  ▼
Traefik в Kubernetes
  │ GatewayClass → Gateway → HTTPRoute
  ▼
Service → Nginx → Hello World!
             │
             └─ stdout access и stderr error → CRI файлы → Fluentd → Loki

Prometheus ← Traefik, node exporter, kube state metrics
Final      ← kubelet и cAdvisor, дополнительные правила и проверки

Final: Grafana → Prometheus и Loki
Final: Prometheus → Alertmanager → локально проверяемый приемник уведомлений
Final: deploy-canary → HTTP smoke и Prometheus → решение оставить canary или вернуть 100/0
```

| Слой | Выбор для MVP | Причина и граница |

| Kubernetes | Один узел kubeadm, containerd, systemd cgroups | kubeadm предпочитается в задании; один узел достаточен для демонстрации, без заявления HA |

| Приложение | Публичный Nginx, совместимый с non-root запуском, ConfigMap со статикой | HTTP 200 и точное тело `Hello World!`, отдельно проверяемые access/error логи |

| Данные | Статические local PV для Prometheus и Loki, локальные позиции и буфер Fluentd | Каталоги и права создает bootstrap; дополнительный storage provisioner и NAS не требуются |

| Выпуск canary в final | Скрипт выпуска с HTTP/metrics gate и автоматическим возвратом 100/0 | Работает через закрепленный механизм управления release; отдельный оператор прогрессивной доставки не требуется |

Это проектные решения, а не проверенная совместимость конкретных релизов. В MVP-00 фиксируется одна совместимая матрица Kubernetes, containerd, Calico, Gateway API CRDs, Traefik chart/image, monitoring chart, Loki, Fluentd и его Loki plugin. Не берем номера версий из разных примеров документации и не используем `latest`, `main` или непроверенный плавающий chart. Версии Kubernetes packages, Helm, Ansible и утилит также фиксируются. Если подходящего публичного Fluentd image с plugin нет, в репозиторий входит Dockerfile с закрепленными зависимостями и автоматическая сборка с загрузкой в containerd или kind.

Предварительный бюджет основной VM: **4 vCPU, 8 GiB RAM, 60 GiB диска**, с возможностью увеличить RAM до 12 GiB. Это начальная оценка, не подтвержденные минимальные требования. В MVP-06 измеряем потребление, свободный диск и время развертывания, после чего указываем проверенный размер в README. Для чистой приемки нужна вторая временная VM либо возврат выделенного стенда к чистому снимку; для параллельного kind нужен отдельный ресурс, не перегружающий основную VM.

Эксперт начинает с обычной Ubuntu 24.04 VM с SSH/sudo, доступом к публичным репозиториям пакетов и образов и сетевым доступом к NodePort. Инструкция по получению такой VM и ее параметры входят в README, но Proxmox, учетная запись в homelab и Nix не становятся зависимостями. Автоматический bootstrap начинается с чистой Ubuntu.

## Общий контракт для агентов

MVP-00 оформляет точные значения в `docs/contracts.md` и `config/versions.yaml`. Предварительно фиксируем следующее:

- Namespaces: `edge` для Traefik, `demo` для Nginx и его Gateway/HTTPRoute, `monitoring` для метрик, `logging` для Fluentd/Loki. Gateway и backend Service находятся в одном namespace.
- Владелец GatewayClass/Gateway только один; автогенерация тех же объектов сторонним chart отключается. Точные listener, Service и container ports согласованы до параллельных сессий.
- MVP отвечает на IP и HTTP NodePort без обязательного hostname. В final новые hostname/path и TLS добавляются так, чтобы базовая проверка сохранялась. Для TLS достаточно `.test` и `curl --resolve`.
- Verify создает уникальные run ID и `X-Request-ID`, отправляет заголовок через Gateway; приложение сохраняет его в JSON access-log и возвращает в HTTP-ответе. Допустимый формат и генерация ID при отсутствии заголовка задаются в контракте. Error-log остается в stderr; missing-file запрос связывается с ним через маркер в URI.
- Request-ID, URL, IP клиента и имя pod не становятся неограниченными Loki/Prometheus labels. В общем прогоне проверяются HTTP counter до/после, успешные scrape и точная запись с Request-ID в Loki; фоновые probes и сбросы counter учитываются.
- Fluentd читает именно файлы Nginx, разбирает оболочку containerd CRI, сохраняет stdout/stderr и доставляет оба потока в Loki. Позиции и файловый буфер переживают рестарт collector. Семантика доставки допускает повторы; exactly-once не заявляется.
- Prometheus собирает метрики Traefik через реальный ServiceMonitor с подходящими namespace/release selectors. Имена metric families и labels подтверждаются на установленной версии.
- Prometheus/Loki доступны эксперту через автоматизированный port-forward, привязанный к loopback. Публичный доступ к административным интерфейсам не нужен.
- Local PV имеют явные node affinity и policy `Retain`; bootstrap создает пути и права. Данные привязаны к одной VM, автоматического failover хранилища нет.
- `deploy` не запускает reset, не удаляет PVC и не перегенерирует существующие секреты. Отдельный cleanup явно различает одноразовый тестовый кластер и постоянный стенд.
- Все ожидания ограничены timeout, ошибки возвращают ненулевой код и понятную диагностику. Уже существующий кластер проверяется на соответствие ожидаемому окружению.
- Verify пишет краткий итог и машинный JSON с профилем, ревизией, временем, статусом каждой проверки, ожидаемым/фактическим результатом и evidence. Набор проверок задан профилем `mvp` или `final`; отсутствие требуемой проверки делает результат неуспешным, автоматического понижения профиля нет. Сетевые проверки создают и удаляют только свои тестовые pod.
- Canary workflow и обычный deploy имеют одного оператора и общую блокировку изменений release. Веса обновляются через тот же источник конфигурации, что deploy. Начальное штатное состояние — stable 100%, canary 0%; успешный canary trial может оставить 90/10 до явно назначенного продвижения. Неудачный кандидат не включается снова обычным повторным deploy.

Предлагаемый интерфейс будущей реализации, **сейчас команды еще не существуют**:

```bash
make bootstrap ENV=ubuntu   # Подготовить ОС, containerd, kubeadm, CNI и каталоги данных
make deploy ENV=ubuntu      # Установить или обновить закрепленные компоненты
make verify ENV=ubuntu      # Готовность, HTTP, Request-ID, метрики, логи и базовые права
make verify-idempotency ENV=ubuntu
make evidence ENV=ubuntu   # Собрать проверяемый отчет без секретов

# В final
make verify ENV=ubuntu PROFILE=final  # Полный набор, включая сетевые security-инварианты
make deploy-canary ENV=ubuntu         # Закрепленный кандидат, проверки и автооткат при отказе
make verify-canary ENV=ubuntu         # Сценарии успешного и неуспешного canary; отдельный тестовый стенд
make ci                    # Статика и одноразовый kind; не использует homelab kubeconfig
make demo ENV=ubuntu       # Воспроизводимая демонстрация дополнительных функций
make package               # Готовит архив после задания URL репозитория и фамилии
```

Порядок с ограничением в четыре одновременно активные сессии: интегратор плюс MVP-01, MVP-02 и MVP-03; после освобождения одного места — MVP-04. Разработка компонентных конфигураций идет параллельно, их проверка на общей VM выполняется последовательно интегратором. Интегратор в это время готовит сборку deploy/verify и документацию.

Приемка MVP обязательна целиком:

- [ ] С чистой Ubuntu 24.04 весь путь выполнен по README без ручного создания или правки Kubernetes-ресурсов.
- [ ] Версии и перечень зависимостей записаны, установка не требует домашних сервисов, приватных образов или registry credentials.
- [ ] Node Ready, DNS и pod network работают, все обязательные workloads готовы.
- [ ] Gateway/HTTPRoute имеют актуальные успешные conditions; curl снаружи кластера идет через Traefik NodePort и получает HTTP 200 с точным ожидаемым телом.
- [ ] Prometheus показывает живой target компонента решения; query возвращает свежие samples, счетчик HTTP меняется после тестовой нагрузки.
- [ ] После запроса с уникальным маркером соответствующий access-log найден через Loki API. Отдельный запрос создает реальную error-запись Nginx, которая тоже найдена в Loki.
- [ ] Один verify-прогон связывает Request-ID в ответе и access-log с проверкой увеличения HTTP counter; отчет содержит ревизию, профиль и результаты readiness, HTTP, metrics, logs и базовых runtime-инвариантов. Провал любого обязательного check дает ненулевой exit code.
- [ ] Повторные bootstrap и deploy не ломают кластер, не создают дубликаты, не стирают данные и проходят тот же verify.
- [ ] В README перечислены ограничения, ресурсы, способы доступа и точные команды проверки; паспорт уже содержит архитектуру и только доказанные возможности.
- [ ] Отчет привязан к ревизии кода и содержит фактические результаты, а не предполагаемое поведение.

После этого фиксируем рабочую ревизию MVP. Если времени на улучшения не осталось, она уже является содержательной основой сдачи; подготовка окончательного паспорта, публичной main и архива все равно обязательна.

| FINAL-01 | Host/path routing, второй Nginx backend, TLS, traffic split, маршруты проверки backend | Gateway API из задания и canary из пользовательского наброска | Высокий |
| FINAL-02 | Grafana, RED и CPU/RAM, поиск логов, alerts и runbooks, отсутствие данных | Мониторинг и логирование из обоих проектов | Высокий |
| FINAL-03 | Проверяемые NetworkPolicy/securityContext, включая запрет app → Kubernetes API | Пользовательские security-инварианты и практики петпроектов | Высокий |
| FINAL-04 | CI: lint, render/schema checks, kind с Calico, полный verify и canary tests | Ephemeral CI из наброска, `check-ops.sh` и GitLab CI из `naeb_goev` | Высокий |
| FINAL-05 | Выпуск canary с автоматическим откатом по HTTP/метрикам, проверки сбоев и состояния | Автооткат из наброска и recovery из петпроектов | Высокий |
| FINAL-06 | Ограниченный набор опций: backup/restore, devShell, SOPS, уведомления | Дополнительные практики homelab | Только после основных улучшений |
| FINAL-07 | Чистая приемка final, паспорт, демонстрация, публичная main и архив | Требования сдачи | Обязателен при любом объеме final |

FINAL-01, FINAL-02 и каркас FINAL-04 можно разрабатывать параллельно после MVP. FINAL-03 готовит отдельные policy manifests и начинает live-проверки после стабилизации потоков. FINAL-05 использует принятые интерфейсы этих задач, выполняется на выделенном стенде с единственным оператором. Итоговая приемка FINAL-04 включает интеграцию security и canary tests после FINAL-03/05. FINAL-06 не входит в критический путь и не должен вытеснять приемку или упаковку.

В final показываем один связный эксплуатационный сценарий: `make verify` с Request-ID и отчетом → TLS и здоровый canary 90/10 → намеренно неуспешная новая версия → автоматическое обнаружение ошибки и возврат 100/0 → повторный verify. Alert и dashboard объясняют событие. Нагрузочные замеры сопровождаем параметрами VM и нагрузки; синтетический локальный результат не превращаем в обещание production SLA.

Критерий автоотката: stable остается рабочим, новая версия проверяется отдельно, метрики свежие и выборка достаточна; при отказе weights действительно возвращаются к 100/0, новые запросы не попадают в canary. Недоступность Prometheus или недостаток данных дает результат `inconclusive` с возвратом на stable и ненулевым кодом выпуска. Ошибка самого возврата — отдельный провал, требующий явной диагностики; такой запуск не называется успешно выполненным rollback.

## Параллельная работа без конфликтов

Один интегратор ведет контракт, версии, Makefile, порядок установки, README и реестр задач. Компонентные агенты владеют только назначенными каталогами и своим отчетом. Каждый Kubernetes-ресурс и каждый Helm release имеют одного владельца.

В текущем `mts_hack` еще нет коммитов, начальная ветка называется `trunk`. Поэтому MVP-00 сначала создает согласованную базовую ревизию и подготавливает `main`; только после этого имеет смысл создавать отдельные ветки и worktree для параллельных задач. В текущей планировочной сессии ветки не менялись и коммиты не создавались.

Каждая реализационная сессия получает отдельный worktree/ветку и зафиксированную базовую ревизию. Не переключать ветки и не выполнять reset в общем checkout. Если worktree недоступны, строгая собственность каталогов обязательна, а интегратор последовательно применяет изменения общих файлов.

**Общей Ubuntu VM и ее kubeconfig управляет только интегратор.** Namespace сам по себе не изолирует изменения CNI, CRDs, GatewayClass, Helm release и cluster-wide RBAC. Компонентным агентам для live-тестов нужны собственные disposable kind/VM; иначе они передают интегратору команды проверки. Проверки отказов, firewall, storage и reset не запускаются параллельно с чужой приемкой.

Отчет каждой сессии: что изменено, базовая и итоговая ревизии, затронутые пути, команды и результаты `pass/fail/not run`, ограничения, изменение контрактов и следующий доступный шаг. Непроведенная live-проверка не становится `pass` из-за успешного render или lint. Полная приемка выполняется после объединения изменений.

## Технические источники для реализации

Выбор базовых механизмов сверялся с официальной документацией. На старте реализации агент проверяет документы именно закрепляемых релизов: страницы `latest` не заменяют матрицу совместимости.

- kubeadm описывает создание Kubernetes-кластера и необходимые ресурсы: [Creating a cluster with kubeadm](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/). Согласование cgroup driver kubelet/containerd: [Container runtimes](https://kubernetes.io/docs/setup/production-environment/container-runtimes/).
- Traefik имеет отдельный Kubernetes Gateway provider, требования к CRDs и RBAC: [Kubernetes Gateway API](https://doc.traefik.io/traefik/reference/install-configuration/providers/kubernetes/kubernetes-gateway/). Маршруты и TLS: [Routing configuration](https://doc.traefik.io/traefik/reference/routing-configuration/kubernetes/gateway-api/).
- Веса backendRefs для разделения HTTP-трафика: [Gateway API traffic splitting](https://gateway-api.sigs.k8s.io/guides/user-guides/traffic-splitting/).
- Для отправки Fluentd в Loki предусмотрен `fluent-plugin-grafana-loki`: [Fluentd client](https://grafana.com/docs/loki/latest/send-data/fluentd/). Позиции чтения и обработка ротации описаны в [Fluentd tail input](https://docs.fluentd.org/input/tail).
- Calico применим для исполнения Kubernetes NetworkPolicy: [Use Calico for NetworkPolicy](https://kubernetes.io/docs/tasks/administer-cluster/network-policy-provider/calico-network-policy/).
- Поведение NetworkPolicy с адресами Service, DNAT и узлами необходимо проверять на выбранном CNI: [Kubernetes Network Policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/). Это особенно существенно для запрета доступа к API на одноузловом kubeadm стенде.
