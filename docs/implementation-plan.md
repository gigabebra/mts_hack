# План работ

Цель — воспроизводимый стенд для задания MTC ENGINEER HACK: простое
HTTP-приложение в Kubernetes, Gateway API, Prometheus и Fluentd.
Среда — отдельная Ubuntu 24.04 VM. Установка и проверка должны выполняться
из репозитория без доступа к инфраструктуре автора.

Основной приоритет — рабочая обязательная часть. Nginx с фиксированным
ответом достаточно, чтобы проверить публикацию, метрики и логи.
Дополнительные функции добавляются после проверки базового стенда.

## Этапы и критерии готовности

| Этап | Что сделать | Как проверить завершение |
| --- | --- | --- |
| 1. Зафиксировать состав | Выбрать совместимые версии компонентов и инструментов | Версии, SHA-256 и image digests записаны в config; неизвестный image отклоняется |
| 2. Поднять кластер | Автоматизировать Ubuntu, runtime, kubeadm, сеть и каталоги данных | Чистая VM дает Ready node; работают DNS и HTTP между Pod и Service; повтор не сбрасывает кластер |
| 3. Опубликовать приложение | Настроить Nginx, Service, GatewayClass, Gateway и HTTPRoute | Внешний запрос возвращает 200 и `Hello World!`; неверный маршрут дает 404 |
| 4. Подключить наблюдаемость | Prometheus собирает targets и HTTP-счетчик; Fluentd передает stdout/stderr в Loki | После запросов растет счетчик и находятся точные access/error-записи |
| 5. Объединить автоматизацию | Один вход установки и общий verify с JSON-отчетом | Ошибка дает ненулевой exit; два повторных deploy сохраняют ресурсы и данные |
| 6. Добавить TLS и canary | HTTPS, два backend, распределение 90/10, проверка кандидата и возврат 100/0 | Неверные CA/имя отклоняются; сломанный кандидат исключается из трафика |
| 7. Проверить восстановление | Прерывание выпуска, замена pod, сохранение истории и буфера логов, reboot | После каждого сценария восстановлено рабочее состояние и проходит verify |
| 8. Повторить с чистой ОС | Новая VM и checkout без готовых инструментов или кэшей | Одного deploy.sh достаточно; инструкции позволяют повторить установку |

Все восемь этапов реализованы и проверены. Ревизии, команды, длительности
и границы прогонов перечислены в [протоколе](verification.md).

## Принятые условия

- Один узел kubeadm, без зависимости от конкретного облачного провайдера.
- Dual-stack: IPv6 основной, IPv4 доступен приложению и компонентам.
- Каждый environment явно указывает VM и kubeconfig. Текущий контекст kubectl
  не используется для выбора стенда.
- Повторный запуск сохраняет кластер. Чужой кластер или изменение его
  идентичности требуют отдельного разбора.
- Credentials, адреса стенда, ключи и kubeconfig хранятся вне Git.
- Автоматические проверки на VM и тесты с моделированными ответами учитываются
  отдельно. Успешная отрисовка YAML не заменяет работающий сервис.

## Что оставлено для развития

Сетевые политики с проверкой разрешенных потоков, Grafana/Alertmanager,
CI с временным Kubernetes и резервное копирование данных. Для них нужны
отдельные критерии проверки; они не включены в текущие заявления о готовности.

План задает ожидаемый результат. ИИ использовался для реализации и тестов;
изменения требований и найденные недостатки отражены в
[истории разработки](development.md).
