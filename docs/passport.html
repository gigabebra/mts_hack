Self-Verifying
Kubernetes Stack

Автоматическая установка и проверка веб-сервиса

Nginx возвращает Hello World! через Kubernetes Gateway API. Prometheus собирает метрики, Fluentd передает access/error-логи в Loki. Сквозная проверка связывает HTTP-ответ и запись лога по Request-ID и отдельно подтверждает прирост HTTP-счетчика.

На схеме показан canary-выпуск 90/10. После установки и отката stable получает 100% трафика. Поддерживаются dual-stack с основным IPv6 и отдельный режим IPv4 без IPv6.

Обязательные компоненты

Из корня репозитория скопируйте подходящий пример из config/environments/ в config/environments/ubuntu.local.yaml, укажите адреса VM, SSH, DNS/NTP и свободные подсети. После проверки SSH выполните bash scripts/deploy.sh --env ubuntu. Скрипт устанавливает инструменты, настраивает ОС и Kubernetes, затем компоненты.

Маршруты Gateway APIЧетыре HTTPRoute: общий маршрут, hostname hello.test и пути к stable/canary с URLRewrite. Отдельные пути проверяют каждый backend при любом общем весе.make verify-release ENV=ubuntu: hostname/path, заголовки маршрута и 404 для неизвестного пути.

Canary и откатДва backend и веса 90/10. Окно 60 с, минимум 100 запросов к canary, максимум 1% 5xx; неверное тело или недостаток данных возвращают 100/0. Это ограничивает влияние ошибочного кандидата.make verify-canary ENV=ubuntu: здоровый кандидат и пять отрицательных сценариев.
НаблюдаемостьHTTP-счетчики и длительность запросов, CPU/RAM узла, состояние Kubernetes и поиск логов в Loki. Один endpoint собирается через одно семейство IP, без удвоения счетчиков.make verify ENV=ubuntu; targets, PromQL и LogQL в README.
Ограничения NginxUID 101, файловая система только для чтения, без capabilities, повышения привилегий и API token. Это сокращает доступ процесса к контейнеру и кластеру.make verify ENV=ubuntu проверяет настройки и работающий процесс.
ВосстановлениеОбработка прерванного Helm upgrade, local PV для истории, позиции и буфер Fluentd на узле. Механизмы сохраняют состояние при замене Pod и кратком отказе.make demo ENV=ubuntu; отдельно с внешней машины: make demo ENV=ubuntu DEMO_ARGS="--section reboot".

Сценарии отказов предназначены для тестовой VM и выполняются последовательно. Они временно меняют состояние стенда и проверяют восстановление. make evidence ENV=ubuntu собирает JSON-отчеты в локальный архив.

Конфигурации: deploy/, ansible/, config/. Сценарии: scripts/ и tests/.

Ревью работы

Главная особенность

Проверяется наблюдаемое поведение: точный HTTP-ответ, изменение счетчика, запись в Loki и восстановление после отказа. JSON-отчеты и ненулевой код при ошибке делают результат каждой проверки доступным для разбора.

Самое сложное решение

Для подтверждения переключения canary сравнивались два подхода: статусы HTTPRoute и фактически обслуживаемые ответы. Выбрано ожидание заголовка X-Traffic-Split, заданного вместе с весами, поскольку Traefik может применять конфигурацию позже обновления статуса; затем измеряется трафик без повторных попыток.

Ограничения

Один узел и local PV не обеспечивают HA или защиту от потери диска; резервного копирования нет. При длительном отказе возможны дубли и потери логов; локальная CA не имеет автоматической ротации. NetworkPolicy, Grafana/Alertmanager и CI не реализованы, откат работает в рамках выпуска.

Предложения по развитию — требование задания

Перечисленные ниже возможности не реализованы и не входят в результаты проверки.

  • NetworkPolicy и уведомления: нужны правила сетевых потоков, тесты разрешений и приемник Alertmanager.
  • CI с временным Kubernetes: нужен runner с ресурсами для VM и доступом к репозиториям зависимостей.
  • Несколько узлов, отказоустойчивое хранилище и backup/restore: нужны дополнительные VM и отдельное хранилище; для телеком-сценариев — стенд отказов каждой IP-семьи.
