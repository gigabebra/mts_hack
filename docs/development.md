# Разработка и принятые решения

Работа строилась вокруг требований автора: воспроизводимая установка
на Ubuntu 24.04, kubeadm, Gateway API, метрики, логи и проверяемый результат.
ИИ использовался для написания Ansible, Helm-конфигураций, Python-скриптов,
тестов и документации. Автор определял приоритеты и уточнял требования
по мере просмотра результата; очередная реализация проверялась теми же
сценариями, которые входят в репозиторий.

## От исходного задания к рабочему стенду

Сначала была собрана обязательная часть: один Kubernetes-узел, Nginx,
Traefik, Prometheus и Fluentd/Loki. Nginx выбран из-за простого проверяемого
ответа; разработка собственной бизнес-логики не помогала решить задачу.
Для установки использованы Ansible и Helm, а Python объединил их запуск
и проверки в общие команды.

Сетевое требование уточнялось отдельно. После варианта с IPv6-only автор
выбрал dual-stack с основным IPv6. В результате оба семейства проверяются
на уровне Pod, Service, внешнего HTTP и логов, а метрики собираются с одного
адреса каждого endpoint, чтобы не удваивать счетчики.

Следующим шагом стали HTTPS и canary. Для них потребовались два отдельных
backend, проверка сертификата, наблюдение за кандидатом и автоматический
возврат на stable. Добавление Grafana, сетевых политик и CI отложено:
сначала требовалось подтвердить установку и восстановление выбранного состава.

## Что исправлялось после проверки

| Наблюдение | Принятая правка | Подтверждение |
| --- | --- | --- |
| Проверка Gateway принимала любой допустимый IPv6, а не адрес выбранного узла | Сравнивать status с `node_ip` environment | Отрицательные тесты и внешний verify |
| Сверки только известного digest недостаточно для image lock | Проверять сочетание repository/tag и digest | Тесты неизвестного repository и tag |
| Актуальные HTTPRoute conditions еще не гарантируют применения весов Traefik | Ждать `X-Traffic-Split`, затем измерять трафик без retries | Проверка 90/10 и отказов кандидата |
| При обновлении canary могли чередоваться ответы старой и новой ревизии | Обновлять кандидата при весе 0 через Recreate и проверять `X-Revision` | Smoke и отказы до/после подачи трафика |
| Успешный ответ stable не доказывал готовность всех replicas | Проверять Helm status, поколение Deployment, rollout, image и values до кандидата, до 90/10 и перед принятием | Регрессионные тесты и три readiness-проверки успешного выпуска |
| Побайтовое сравнение position file Fluentd не учитывало удаление неактивной истории | Сравнивать активные источники, inode, размеры, offsets и повторное чтение | Буферизация и рестарт Fluentd |
| Чистая установка не должна зависеть от заранее подготовленных инструментов | Объединить зависимости, bootstrap и компоненты в deploy.sh; при ошибке bootstrap остановить установку | Две новые Ubuntu VM без Kubernetes, Helm, Ansible, make и Python venv |

Эти замечания зафиксированы в истории изменений и подтверждены тестами.
Проверки на VM запускались автоматизацией с помощью ИИ; их машинные результаты
приведены в [протоколе](verification.md).

## Проверка перед сдачей

После реализации автор отдельно потребовал повторить установку на чистой VM
и убедиться, что все установочные действия выполняет скрипт. Повтор занял
5 минут 45 секунд; ручных установочных шагов не потребовалось. Затем прошли
два повторных deploy, внешние HTTP/TLS-проверки и перезагрузка.

Последнее требование к оформлению — убрать внутренние рабочие записи,
свести план и историю изменений в понятные документы, сохранить команды
воспроизведения и результаты проверок. Старые промежуточные документы
доступны в Git; актуальная документация описывает сдаваемое решение.
