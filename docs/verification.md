# Результаты проверки

Решение проверено на Ubuntu 24.04.5 LTS amd64: 4 vCPU, 8 GiB RAM,
диск 60 GiB. Локальные тесты и проверки работающего Kubernetes учитываются
отдельно. Таблицы описывают сохраненные прогоны; изменение документации
не означает повторного запуска установки.

Сохранённые прогоны ниже выполнены до изменения сбора Git-метаданных:
теперь установка и проверки поддерживают копию исходников без `.git` и Git.
Отсутствие этих метаданных обозначается `null` в полях `revision` и
`working_tree_dirty` и не влияет на результат проверки. Исторические хеши
и числа тестов в протоколах сохранены; они относятся к указанным там версиям.

| Полная проверка dual-stack | `c268c5fb47759db76a661a014ffd56a8974c8f51` | Чистая установка и тот же набор сценариев отказов и восстановления |
| Повтор чистой установки dual-stack | `27d775b76a5ae0021911293de137a4c3d5efc53c` | Еще одна чистая VM, HTTP/TLS, метрики и логи, повторное развертывание и перезагрузка |

Исполняемый код двух dual-stack-ревизий одинаков. Проверка IPv4 выполнена
на измененном рабочем дереве: его точный состав зафиксирован в
`tested_files_sha256`. С тем же кодом также проверен существующий
dual-stack-кластер без повторной установки и инъекции отказов.

Машинные сводки: [IPv4](evidence/ipv4-validation.json),
[полная проверка dual-stack](evidence/full-validation.json),
[повтор установки dual-stack](evidence/clean-install.json).
В них сохранены исходные идентификаторы запусков, временные поля и хеши:
это данные протоколов, а не отметки о готовности документации.
Полные локальные отчеты из `artifacts/` не входят в публичный репозиторий;
их пути в сводках обозначают исходные артефакты проверки.

## Чистая установка

До установки отсутствовали Kubernetes, containerd, Helm, Ansible
и каталоги предыдущего кластера. Передавались исходники, SSH-доступ
и локальная конфигурация, без готовых кэшей и инструментов проекта.
Первая установочная команда — `bash scripts/deploy.sh --env ubuntu`;
предварительные `make tools` и `make bootstrap` не требовались.

| Команда | IPv4 без IPv6 | Dual-stack, полный прогон | Dual-stack, повтор |
| --- | --- | --- | --- |
| `bash scripts/deploy.sh --env ubuntu` | Успех, 393,41 с | Успех, 312,30 с | Успех, 345,15 с |
| `make lint` | 193 теста прошли, 2 пропущены | 180 тестов прошли | 180 тестов прошли |
| `make health ENV=ubuntu` | Успех | Успех | Успех |
| `make verify-release ENV=ubuntu` | Успех | Успех | Успех |
| `make verify-idempotency ENV=ubuntu` | Успех | Успех | Успех |
| `make demo ENV=ubuntu` | Успех | Успех | Не запускалась |
| `make evidence ENV=ubuntu` | Отчеты собраны | Отчеты собраны | Отчеты собраны |

Создание VM, передача исходников и подготовка SSH в эти длительности
не входят. Локальные проверки включают синтаксис Python/Ansible/YAML,
Helm lint/render семи charts и закрепление образов. Для кода с поддержкой
IPv4 проверены оба сетевых режима; на Ubuntu с IPv6 прошли все 195 тестов.

## IPv4 без IPv6

На VM IPv6 отключен параметром ядра `ipv6.disable=1` до установки.
IPv6-адресов нет, создание сокета `AF_INET6` возвращает `EAFNOSUPPORT`
(errno 97). Это подтверждено и после перезагрузки. Использовано ядро
`6.8.0-142-generic` и конфигурация на основе
[примера IPv4](../config/environments/ubuntu-ipv4.example.yaml).

Проверены одно семейство адресов Pod/Service, один Calico IPPool,
DNS A, прямой доступ к Pod и через Service. Два пропущенных локальных
теста требуют IPv6 loopback; Helm lint/render обоих режимов прошли.
Попытка сменить сетевой режим установленного кластера на dual-stack
отклонена в Ansible check mode до настройки ОС.

Пять проверок TLS/Gateway на VM выполнили по 140 проверок.
При весах 90/10 из 1000 запросов 100 получил canary, ошибок не было.
После возврата 100/0 трафик обслуживал только stable.

## HTTP, метрики и логи

Сквозная проверка подтверждает:

- HTTP 200 и точное тело `Hello World!`; корректный Request-ID сохраняется,
  невалидный заменяется. Неверный маршрут и отсутствующий файл дают 404.
- Готовность компонентов, адреса Pod/Service и EndpointSlices выбранного режима.
- Здоровые targets Prometheus, свежие samples и прирост HTTP-счетчика
  без двойного сбора одного endpoint.
- Access-запись в Loki с тем же Request-ID, методом, URI и status;
  отдельную stderr-запись об отсутствующем файле.
- Nginx с UID 101, без capabilities и API token, с файловой системой
  контейнера только для чтения.

В dual-stack проверяются обе семьи IP. TLS/Gateway выполняет 154 проверки;
неверные CA и hostname отклоняются с `curl_exit: 60`, без `-k`.
В полном прогоне из 1000 запросов canary получил 99 по IPv6 и 100 по IPv4,
ошибок не было. Проверка существующего dual-stack-кластера кодом
с поддержкой IPv4 также прошла.

## Canary и восстановление

В полных прогонах IPv4 и dual-stack получены следующие результаты:

| Сценарий | Ожидаемый и полученный результат |
| --- | --- |
| Здоровый кандидат | `accepted`; проверены HTTP и метрики backend |
| HTTP 500 после включения 90/10 | `rejected`; восстановлены веса 100/0 |
| HTTP 200 с неверным телом после 90/10 | `rejected`, несмотря на отсутствие 5xx |
| Неверное тело до подачи общего трафика | `rejected`; 90/10 не включались |
| Недоступные метрики | `inconclusive`; возврат 100/0 |
| Недостаточная выборка | `inconclusive`; возврат 100/0 |
| Прерывание Helm upgrade | Восстановление безопасной ревизии в том же и следующем запуске |
| Замена Pod приложения и откат конфигурации | Восстановление приложения; версия подтверждена HTTP-ответами |
| Замена Pod Prometheus и Loki | Ранее записанная история сохранилась в PVC |
| Недоступность Loki и перезапуск Fluentd | Отложенные записи доставлены, активные позиции чтения сохранены |

Дочерние отчеты отрицательных сценариев сохраняют `status: fail`.
Успех общего сценария означает правильное обнаружение отказа
и восстановление. В полной dual-stack-проверке коды шести canary-сценариев
вычислены из результатов вызова внутри процесса; фактические коды дочерних
процессов отдельно проверены сценариями прерывания.

Готовность stable проверяется до установки кандидата, до 90/10 и перед
принятием. Состояния Helm pending/failed, устаревшее поколение Deployment
и неполные реплики проверены локальными регрессионными тестами.
Отдельная инъекция деградации stable на работающем кластере не выполнялась.

## Повторное развертывание и перезагрузка

Каждая проверка идемпотентности дважды выполняет bootstrap/deploy/verify.
В повторном dual-stack-прогоне сохранены 28 идентификаторов ресурсов,
привязки двух PVC и содержимое пяти прикладных Secrets, включая сертификаты.

Перезагрузка проверена с внешней управляющей машины: подтверждены смена
boot ID, восстановление API, успешные health и verify-release. Время
готовности API — 35,04 с для IPv4, 34,85 с и 35,73 с для двух dual-stack-VM.
Это проверка восстановления одного узла; отказоустойчивость нескольких
узлов она не подтверждает.

В исходном протоколе полной dual-stack-проверки сохранена ошибка ожидания
штатного выключения временной VM: остановка заняла больше 90 секунд.
Последующая проверка подтвердила выключение без принудительной остановки;
ошибка не относится к сценарию перезагрузки.

## Границы результатов

Повтор чистой dual-stack-установки не включает повторные canary-сценарии,
прерывание выпуска и восстановление PVC/буфера. Минимальные ресурсы,
предельная нагрузка и сохранность логов при длительном отказе не определялись.
NetworkPolicy, Grafana/Alertmanager, CI и резервное копирование не реализованы.

Команды воспроизведения находятся в [README](../README.md)
и [инструкции по эксплуатации](operations.md).
