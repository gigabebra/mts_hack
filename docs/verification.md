# Результаты проверки

Новый режим `ipv4` проверен отдельно на VM с отключенным IPv6:
[полный прогон IPv4-only](#ipv4-only-на-vm-без-ipv6).
Приведенные ниже результаты двух прежних dual-stack установок сохранены
как исторические; их ревизии не относятся к новому прогону.

Решение проверено на Ubuntu 24.04.5 LTS amd64: 4 vCPU, 8 GiB RAM,
диск 60 GiB. Ниже разделены два прогона от 3 октября 2026 года.
Команды запускались автоматизацией с помощью ИИ. Локальные unit-тесты
и проверки реального Kubernetes учитываются отдельно.

| Прогон | Проверенная ревизия | Состав |
| --- | --- | --- |
| Полная проверка | `c268c5fb47759db76a661a014ffd56a8974c8f51` | Чистая установка, TLS, canary/rollback, interruption, восстановление, повторный deploy и reboot |
| Повтор чистой установки | `27d775b76a5ae0021911293de137a4c3d5efc53c` | Еще одна чистая VM, сквозная проверка, два повторных deploy, внешний HTTP/TLS и reboot |

Исполняемый код этих ревизий одинаков; между ними менялись документы.
Подготовка документации к сдаче не является новым прогоном установки.
Машинные сводки: [полная проверка](evidence/full-validation.json) и
[повтор установки](evidence/clean-install.json). Они содержат исходные ревизии
и SHA-256 отчетов. Оригинальные протоколы сохранены в Git по ссылкам
`original_report` внутри JSON; результаты не пересчитаны задним числом.

## Чистая установка

Перед обоими прогонами отсутствовали Kubernetes, containerd, Helm, Ansible,
make, Python venv и каталоги предыдущего кластера. Передавались только
исходники, SSH-доступ и локальный environment, без готовых кэшей и tools.
Первой установочной командой была `bash scripts/deploy.sh --env ubuntu`.
Предварительных `make tools`, `make bootstrap` и ручных Kubernetes-команд
не было. Оба запуска завершились с exit 0.

| Команда | Полный прогон | Повтор установки |
| --- | ---: | ---: |
| `bash scripts/deploy.sh --env ubuntu` | pass, 312,30 с | pass, 345,15 с |
| `make lint` | pass, 15,67 с | pass, 16,05 с |
| `make health ENV=ubuntu` | pass, 46,35 с | pass, 45,87 с |
| `make verify-release ENV=ubuntu` | pass, 26,69 с | pass, 26,68 с |
| `make verify-idempotency ENV=ubuntu` | pass, 267,83 с | pass, 326,60 с |
| `make demo ENV=ubuntu` | pass, 918,13 с | not run: повтор ограничен установкой |
| `make evidence ENV=ubuntu` | pass, 0,20 с | pass, 0,11 с |

Создание VM, передача checkout и подготовка SSH/environment в эти времена
не входят. Reboot и внешние проверки выполнялись дополнительно.
Во втором прогоне при старте Calico были временные ошибки создания pod-сети;
они разрешились автоматически в пределах штатных ожиданий установщика.

`make lint` в каждом прогоне выполнил 180 тестов в 9 suites, проверки
Python/Ansible/YAML, lint/render семи Helm charts и image lock.
Отдельно проверено отклонение неправильных аргументов deploy.sh до установки.

## Приложение, метрики и логи

В полном прогоне выполнены девять базовых verify, в повторе — четыре.
Каждый прошел 11 основных проверок: readiness, обе сети, Gateway conditions,
подготовка и снимок метрик, HTTP IPv6/IPv4, прирост счетчика, логи обеих семей
и runtime security.

- HTTP 200 и точное тело `Hello World!`; корректный Request-ID сохраняется,
  невалидный заменяется. Неверный маршрут и отсутствующий файл дают 404.
- Prometheus видит здоровые targets и свежие samples без двойного scrape.
  Во втором прогоне приросты HTTP-счетчика составили 48, 49, 49 и 48
  при минимуме 48 в каждом verify.
- Loki возвращает access-запись с тем же Request-ID и отдельную stderr-запись
  об отсутствующем файле. Проверяются метод, URI, status и source labels.
- Процесс Nginx работает с UID 101, без capabilities и API token,
  с read-only root filesystem.

TLS/Gateway: шесть проверок по 154 checks в полном прогоне и две в повторе,
плюс внешняя проверка каждого стенда. Неверные CA и hostname отклонялись
с `curl_exit: 60` по обеим семьям; `-k` не использовался.
При распределении 90/10 из 1000 запросов canary получил 99 по IPv6 и 100
по IPv4, ошибок не было. После возврата 100/0 трафик обслуживал только stable.

## Canary и восстановление

Следующие результаты относятся к полному прогону:

| Сценарий | Решение и результат |
| --- | --- |
| Здоровый кандидат | accepted; 2400 HTTP за 60 с, 240 ответов canary, backend delta 241, 5xx 0% |
| HTTP 500 после включения 90/10 | rejected; ошибочный кандидат исключен, восстановлены 100/0 |
| HTTP 200 с неверным телом после 90/10 | rejected по проверке тела, несмотря на 0% 5xx |
| Неверное тело до подачи трафика | rejected; 90/10 не включались |
| Недоступные метрики | inconclusive после реального закрытия port-forward; возврат 100/0 |
| Недостаточная выборка | inconclusive; backend delta 2 при минимуме 100; возврат 100/0 |
| Прерывание Helm upgrade | Восстановление безопасной ревизии в том же и следующем запуске |
| Замена app pod и rollback конфигурации | Приложение восстановилось; версия подтверждена HTTP-ответами |
| Замена Prometheus/Loki pod | Ранее записанная история сохранилась в PVC |
| Недоступность Loki и рестарт Fluentd | Доставлены все 5 marker-записей; активные offsets сохранены, replay 0 |

В пяти отрицательных canary-сценариях подтверждены 25/25 ответов stable
и 5/5 ответов восстановленного кандидата. Дочерние отчеты об отказах сохраняют
`status: fail`; успех общего теста означает правильное обнаружение отказа
и восстановление. Поля exit code этих шести случаев вычислены из результата
вызова внутри процесса; реальные subprocess exit codes отдельно проверены
сценариями interruption.

Готовность stable проверяется до установки кандидата, до 90/10 и перед
принятием. В live-выпуске прошли все три проверки. Состояния pending/failed
Helm, устаревшее поколение и неполные replicas проверены регрессионными тестами;
отдельная live-инъекция деградации stable не выполнялась.

## Повторный запуск и reboot

Каждый idempotency-прогон дважды выполнил полный bootstrap/deploy/verify.
Во втором прогоне сохранены 28 identities, привязки двух PVC и содержимое
пяти прикладных Secrets. Проверка сертификатов входит в это сравнение.

Reboot подтвердил смену boot ID и возврат API за 34,85 с и 35,73 с
соответственно. После него прошли health и verify-release, службы запускались
автоматически. Это проверка восстановления одной VM, не доказательство HA.

Во время завершения первого полного прогона штатное выключение временной VM
превысило ожидание 90 секунд и вернуло ошибку. Последующая проверка подтвердила
остановку; принудительное выключение не выполнялось. Эта ошибка не относится
к успешному reboot и сохранена в исходном протоколе.

## Что этими прогонами не проверялось

Во втором прогоне повторно не запускались canary fault/rollback, interruption
и PVC/buffer recovery. Сетевые политики, Grafana/alerts, hosted CI и backup
не реализованы. Не определялись минимальные ресурсы, предельная нагрузка
и гарантии сохранения логов при длительном сбое.

Команды для воспроизведения и диагностики находятся в
[README](../README.md) и [инструкции по эксплуатации](operations.md).

## IPv4-only на VM без IPv6

4 октября 2026 года (МСК) завершен отдельный полный прогон новой конфигурации
`network_mode: ipv4` на чистой Ubuntu 24.04.5 LTS: 4 vCPU, 8 GiB RAM, диск 60 GiB,
ядро `6.8.0-142-generic`. IPv6 отключен параметром ядра `ipv6.disable=1`
до первой установки проекта. IPv6-адресов нет, создание сокета `AF_INET6`
возвращает `EAFNOSUPPORT` (errno 97). Это повторно подтверждено после reboot.

До установки на VM отсутствовали Kubernetes, containerd, Helm, Ansible
и каталоги предыдущего кластера. Первая команда проекта —
`bash scripts/deploy.sh --env ubuntu`. Конфигурация соответствует
[примеру IPv4](../config/environments/ubuntu-ipv4.example.yaml), с адресами
тестового стенда и доступными ему IPv4 DNS/NTP.

| Проверка | Результат | Время |
| --- | --- | --- |
| Установка с нуля | pass | 6 мин 33 с |
| `make lint` | 193 теста прошли, 2 IPv6 transport-теста пропущены; Helm lint/render обоих режимов прошли | 21 с |
| `make health ENV=ubuntu` | pass | 48 с |
| `make verify-release ENV=ubuntu` | IPv4-сеть, HTTP/TLS, метрики и логи: pass | 26 с |
| `make verify-idempotency ENV=ubuntu` | Два повторных bootstrap/deploy/verify: pass | 4 мин 58 с |
| `make demo ENV=ubuntu` | Все canary, interruption и recovery-сценарии: pass | 14 мин 47 с |
| `make evidence ENV=ubuntu` | Отчеты собраны | менее 1 с |
| Reboot с внешнего контроллера | Новый boot ID, затем health и verify-release: pass | 2 мин 22 с |

В IPv4-режиме проверены одна семья адресов Pod/Service, один Calico IPPool,
DNS A, прямой доступ к Pod и через Service. Каждый из пяти TLS/Gateway-прогонов
на самой VM выполнил 140 проверок. При весах 90/10 из 1000 запросов 100
получил canary, ошибок не было. После возврата 100/0 трафик шел на stable.

Все шесть canary-сценариев дали ожидаемые решения: здоровый кандидат принят;
HTTP 500, неверное тело и неверное тело до подачи трафика отклонены;
недоступные метрики и недостаточная выборка дали `inconclusive`.
После отрицательных сценариев подтверждено восстановление 100/0.
Прерывание Helm upgrade восстановлено в том же и следующем запуске.
Замена app pod и rollback конфигурации, сохранение истории Prometheus/Loki
при замене pod, а также доставка логов после недоступности Loki и замены
Fluentd прошли. Ожидаемые отказы кандидатов сохраняют `status: fail`
в дочерних отчетах; общий приемочный отчет имеет `status: pass`.

Reboot выполнен отдельно командой
`make demo ENV=ipv4-acceptance DEMO_ARGS="--section reboot"`
с внешнего контроллера. API стал готов за 35,04 с. После перезагрузки
подтверждены отсутствие IPv6, готовность сервисов, HTTP/TLS, метрики и логи.
Попытка изменить установленный IPv4-кластер на dual-stack проверена через
Ansible check mode: защита отклоняет изменение до настройки ОС.

На отдельной Ubuntu с IPv6 прошли все 195 тестов без пропусков и Helm
lint/render обоих режимов. Проверка существующего dual-stack-кластера новым
кодом также прошла: обе семьи адресов, HTTP, метрики, логи и 154 TLS/Gateway
проверки. Повторная установка и инъекции отказов на этом кластере не выполнялись.

[Машинный отчет](evidence/ipv4-validation.json) содержит команды, длительности,
результаты, хеши отчетов и 101 проверенного файла кода, конфигурации и тестов.
Проверялось измененное рабочее дерево, а не отдельный новый commit.
Полные JSON-отчеты собраны локально в
`artifacts/evidence/ipv4-validation-20261004.tar.gz`.
