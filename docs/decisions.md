# Технические решения

Проект объединяет установку Kubernetes, публикацию Nginx через Gateway API,
метрики Prometheus и логи Fluentd/Loki. Конфигурации, скрипты, тесты
и документация разработаны с использованием ИИ; автор задавал требования
и проверял результаты. Ниже описаны решения, используемые в текущем коде.

## Состав и автоматизация

| Решение | Обоснование | Реализация |
| --- | --- | --- |
| kubeadm на одной Ubuntu VM | Воспроизведение без инфраструктуры автора и привязки к облаку | [Ansible](../ansible/README.md) настраивает ОС, containerd, Kubernetes и Calico |
| Nginx с фиксированным ответом | Точное тело ответа позволяет обнаружить ошибку приложения, даже если HTTP status равен 200 | [Chart приложения](../deploy/app/values.yaml), заголовки `X-Release` и `X-Revision` |
| Ansible, Helm и Python | Ansible управляет узлом, Helm — ресурсами, Python объединяет установку и проверки | [deploy.sh](../scripts/deploy.sh) и [deploy.py](../scripts/deploy.py) |
| Явная конфигурация окружения | Команда должна обращаться к выбранной VM независимо от текущего kubectl context | `config/environments/<ENV>.local.yaml`, явный kubeconfig и проверка принадлежности кластера |
| Версии, SHA-256 и digest | Повторная установка использует закрепленные зависимости | [versions.yaml](../config/versions.yaml), [images.lock.yaml](../config/images.lock.yaml), проверка пары repository/tag и digest |

## Сеть и наблюдаемость

В `dual-stack` IPv6 является основным, IPv4 доступен параллельно. Для VM
без IPv6 предусмотрен отдельный режим `ipv4`. Режим задается до установки
и входит в неизменяемые параметры кластера; автоматического переключения нет.

Prometheus собирает каждый endpoint через одно семейство адресов, чтобы
не удваивать счетчики. Request-ID остается полем лога и HTTP-заголовком:
он связывает запрос с записью в Loki без создания отдельной серии метрик
для каждого запроса. Проверка прироста счетчика выполняется отдельно
и учитывает возможность фонового трафика.

Fluentd сохраняет позиции чтения и файловый буфер на узле. Local PV
сохраняют историю Prometheus и Loki при замене Pod; эти механизмы
не обеспечивают резервного копирования или защиты от потери диска.

## Выпуск и восстановление

Наиболее сложное решение — подтверждение фактического переключения трафика.
Проверка только статусов HTTPRoute недостаточна: Traefik может еще обслуживать
предыдущую конфигурацию. Скрипт ожидает `X-Traffic-Split`, заданный вместе
с весами, затем измеряет реальные ответы без повторных попыток.

| Механизм | Назначение | Проверка |
| --- | --- | --- |
| Canary обновляется через Recreate при весе 0 | Исключает чередование старой и новой ревизий кандидата | Отдельный маршрут и `X-Revision` |
| Stable проверяется до кандидата, до 90/10 и перед принятием | Подтверждает готовность всех реплик, версии и значений Helm | Проверки Helm status, поколения Deployment, образа и values |
| Недостаток метрик дает `inconclusive` | Отсутствие данных не считается подтверждением качества кандидата | Возврат 100/0 и ненулевой код выпуска |
| Прерванный выпуск восстанавливается по состоянию кластера | Локальный отчет не определяет фактические веса и ревизию Helm | Безопасная завершенная ревизия и проверка stable-трафика |
| Проверка активных позиций Fluentd | Учитывает ротацию файлов и удаление неактивной истории | Источники, inode, размеры, offsets и повторное чтение |

Главная особенность проекта — проверка наблюдаемого результата: ответа HTTP,
прироста счетчика, точной записи в Loki и восстановления после отказа.
Сценарии и границы подтвержденных результатов описаны в
[результатах проверки](verification.md).
